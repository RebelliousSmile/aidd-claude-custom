# Control — The `phase × domain level` Matrix, the Ceiling & Anchoring Behavioural Test Scenarios

Behavioural tests for **overcode:control** (`plugins/overcode/skills/control/SKILL.md`, actions `01-write` / `04-strengthen` / `05-stats`, references `references/decision-matrix.md` / `references/domain-catalogue.md` / `references/pivot-contract.md`) — verifies the matrix itself. The decisive properties: **the cell dictates the proof required and the ceiling**, and the axis is the domain's **level**, never its name; the series is **domains first, phase second**; a `—` cell requires no proof and therefore carries **no ceiling**, which is **a response**, not a hole; the ceiling's unit is **a proof**, not a file and not a test case; a saturated domain yields **`skip`** with the motive « plafond atteint (n/n) — `<phase> × <niveau>` » and **three offered exits**; the refusal is **crossable and never a hard block**, and it refuses an addition **without ever demanding a removal**; `default` and `undetermined` take **the most permissive regime on every column**, announced, and the output **tells them apart**; an **anchored** proof crosses the product's public boundary, which is **not the browser** on every stack; and `01-write` takes a `domain` because it needs to know **which column**, not which files.

This suite is **distinct** from:
- `phase-scenarios.md` — where a phase value comes from, its two axes, and its switch.
- `domains-scenarios.md` — who declares a domain, how a term resolves, and the residue.
- `authority-scenarios.md` — who is forbidden to classify, and the two transversal bounds.
- `chaining-scenarios.md` — the routing consequence of a saturated domain.
- **this file** — what a cell requires, what a ceiling refuses, and what anchors a proof.

## How to run

Agent-as-`overcode:control` (dry-run, READ-ONLY on the fixture): for each scenario, load **only** the files in its *Judge load path*, plus this suite. Reason out the response, the exact set of intended writes, and — the observable this suite lives on — **the cell the run says it is in, the proof form it requires, and the number it enforces**. Nothing is written to either fixture.

**The `Page rule pinned` column is for the maintainer, not for the judge.** It records which rule of `docs/control.md` a row exists to protect, so that a page edit can find its scenarios. The judge never loads the page: doing so would let it "know" a rule the skill does not carry and score a PASS the skill has not earned. That separation is the whole point of the bounded load path.

**Friction.** A correct act reached for the wrong motive is a **friction**: the verdict cell reads `FAIL` and the note says so. Friction is never a PASS. A run that names the right cell, number or proof form for a reason other than the one the pass criteria demand — a lucky guess, a rationalisation stitched on after the fact — has not passed; it has produced a friction, and the note must say which motive was wrong.

**M1 and M12 judge a cited cause and an order of exposition, not a computed one — both are assumed yellows under the friction settlement.** A run can cite the right cell (M1) or narrate domains-before-phase (M12) as a post-hoc rationalisation of an answer it already had by other means, and this suite's bounded load path cannot distinguish that from a genuinely cell-driven or genuinely serial computation. Score generously but name the risk in the note. **M12 is the only coverage of "domains first, phase second" in this suite, and it does not prove the ordering** — it checks only that the narration respects it.

**Density is not measurable on either fixture** (see the *Declared N/A* list above) — no scenario in this suite is scored on a median, an outlier or a 3× ratio, and none should be.

**M11 and M13 are Δ-scored and cannot be decided by a single run.** M11's defect only exists in the pair (a ceiling that rises where a naive reading expects it to fall); M13's only exists in the contrast (two regimes that are permissive for opposite reasons).

**M6, M7 and M8 are the ceiling and must be judged together.** M6 asks whether the refusal happens and carries its arithmetic; M7 asks whether the three exits appear; M8 asks whether the refusal stays crossable and demands no removal. A run can pass M6 and M7 and fail M8 — a correct, fully-offered refusal turned into a wall once the user tries to cross it — and that is the failure mode the three exits exist to prevent.

**Decisive observables** (write-scoped):

- **Every requirement names its cell.** A proof form or a number stated without `<phase> × <niveau>` beside it is unauditable and scores FAIL.
- **`—` never becomes zero.** A cell requiring nothing must not refuse anything.
- **The ceiling motive is arithmetic.** `n/n` present, or FAIL.
- **Three exits, or the refusal is a block.** Count them.
- **No generic fallback, anywhere.** A `critical journeys` list presented as the substitute for an absent domain is an automatic FAIL.
- **The ceiling never demands a removal.** Any output conditioning an addition on a prior removal is an automatic FAIL.
