# Control — Routing Graph, Chaining Contract & Halting Cases Behavioural Test Scenarios

<!--

Behavioural tests for **overcode:control** (`plugins/overcode/skills/control/SKILL.md`, all six actions) — verifies the routing graph and the contract carried by each edge. The decisive properties: `05-stats` is the entry point, routes, and **launches nothing**; no state survives between two runs; **the one who names hands over, the one who receives does not recompute**; `01-write` is the sink and every confirmed gap crosses it **one at a time, the number constraint re-evaluated between each**; `02-audit` has **no edge** to `01-write`; `03-configure` is reachable and terminal; `scope` + `domain` together halts; no test file found → no ranking at all; and saturation is answered with a narrower `scope`, **never with a `domain`**.

This suite is **distinct** from:
- `matrix-scenarios.md` — what a cell requires and what its ceiling **number** is, cell by cell. Here (S14, S15): once a cell is saturated, which routes the run actually takes next — the three exits as edges of the graph, not as matrix content. `matrix-scenarios.md` does not test routing.
- `phase-scenarios.md` — `03-configure` taking none of the three parameters (there: as a parameter rule; here: as a graph position).
- `confirmations-scenarios.md` — whether an act may be confirmed as a batch.
- `measurement-scenarios.md` — the degenerate measurement cases and their order.
- **this file** — which edges exist, what travels along them, and where a run stops.

## How to run

Agent-as-`overcode:control` (dry-run, READ-ONLY on the fixture): for each scenario, load **only** the files in its *Judge load path*, plus this suite. Reason out the response, the exact set of intended writes, **and the set of actions the run would invoke**, then judge against the pass criteria.

**The invocation set is a first-class observable here.** Half this suite turns on the difference between *naming* an action and *launching* it. Record, for every run, the list of actions the skill would actually execute — a suite that only reads the prose will score S1 as a PASS on the strength of the word "suggests".

**S2 requires two runs and is judged on the Δ.** Run 1 answers the phase question out loud; run 2 is a clean invocation. Anything carried into run 2 that was never written to the project document is retained state. **This is only decidable from a fresh judge context**: whichever agent or session reasons about run 2 must not be the same one that held run 1 in its own context, or "no retained state" is true by construction of the test rather than observed in the skill. If a single-context judge is unavoidable, fall back to an artefact-based observable: run 2's output must cite nothing but a fresh read of the project document and the repo — no reference to run 1's answered phase or domain unless that value is also freshly re-derived in run 2.

**Maintainer note, not scored (S13).** The delegation targets named in `aidd-dev:06-test` — `01-test` for `contract`, `02-test-journey` for `e2e` — are a real fact of that skill, not a rule of `docs/control.md`. S13 scores only that exactly two delegations occur and that `skip` delegates to nothing; it does not score which named sub-action of `06-test` is invoked.

**S9 and S14 are the two saturations, and they must be scored against each other.** Both end in a refusal to add, and each has its own remedy: S9 saturates a **population** — too many candidates for one pass — and is answered with a **narrower `scope`**; S14 saturates a **cell** — the ceiling of a `phase × niveau` column — and is answered by **offering** a phase, a removal, or a forced decision, the choice staying the user's. Score the pair together on every run: a remedy borrowed from the other scenario is a FAIL on both, because the two runs are then indistinguishable and the skill is treating volume and authority as the same problem.

**The `Page rule pinned` column is for the maintainer, not for the judge.** It records which rule of `docs/control.md` a row protects, so that a page edit can find the scenarios that guard it. The judge never loads the page — its reading is bounded by the *Judge load path* column.

**Rewrite log — S14 and S15, 2026-07-29 (DEC-006).** Both rows were rewritten, not deleted, and the motive is the page. S14 required the three exits to be *named as routes*; `docs/control.md:68` states the opposite — « la skill propose, l'utilisateur choisit » — so an exit that routes on its own decides in the user's place. The row now scores the offer and fails any automatic routing. S15 required the ceiling-saturated candidate to be *returned to `02-audit`*; the same line states that the ceiling « refuse un ajout, il n'exige jamais un retrait », so that referral is the one edge the model deliberately does not have — S15 was pinning an edge nobody claimed. The row now scores what `04-strengthen` does claim: the constat is reported next to the row, the row stays on the same footing, and the refusal belongs to `01-write` at handoff. Neither rewrite relaxes a criterion; both re-aim one at the rule actually in force.

**Decisive observables** (write-scoped):

- **`05-stats` intended writes = ∅ and invocations = ∅.** Named actions only.
- **No `02-audit` → `01-write` edge**, in either the prose or the invocation set.
- **One measurement, one computation.** A value recomputed downstream is a FAIL even when the two agree.
- **`scope` + `domain` → halt.** Any output past that point is a FAIL.
- **Population saturation remedy = `scope`** (S9). A `domain` offered as the remedy is an automatic FAIL.
- **Ceiling saturation remedy = three exits** (S14), each **offered to the user, none applied by the run**. A `scope` offered as the remedy is an automatic FAIL, and so is any automatic routing of the case — including to `02-audit`.
- **No edge out of `skip`.** The invocation set is counted per tier, not read from the prose.
