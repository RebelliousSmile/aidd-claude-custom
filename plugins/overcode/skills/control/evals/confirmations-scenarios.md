Behavioural tests for **overcode:control** (`plugins/overcode/skills/control/SKILL.md`, actions `02-audit` / `03-configure` / `04-strengthen` / `06-align`) — verifies the confirmation regime. The decisive properties: the regime covers **three acts**, not one — deleting a test, applying a config fix, writing a proposed test; the default is **line by line** and the phase never moves a line across it; a user may name a batch **for removals only**, and the asymmetry's motive is arithmetic, not caution; the one exception is `06-align` on a phase switch, whose batch requires **four components, all of them**, whose refusal is en bloc with **no per-item fallback**, and whose outgoing set requires **both** motives; three named categories plus a catch-all are excluded from every batch; an **empty batch is a legitimate result**; and — the part 2 addition — nothing the matrix produces ever enters a removal batch: a cell that requires nothing qualifies no removal, and a saturated ceiling refuses an addition without ever asking for one back.

This suite is **distinct** from:
- `chaining-scenarios.md` — the one-at-a-time handover to `01-write` as a graph property, and where a saturated ceiling routes the run.
- `phase-scenarios.md` — whether `undetermined` participates in a switch at all.
- `matrix-scenarios.md` — what a cell requires and what its ceiling is. This suite takes the cell as given and asks only what may be confirmed at once.
- `align-write-scenarios.md` — what `06-align` writes into the document once the batch is settled.
- **this file** — what the user is asked to approve, and in what unit.

> **Fixture / preconditions.** Run against a **populated** Python repo, **READ-ONLY**. Nothing is deleted, written or applied; the observable is the approval unit the skill *would* ask for.
>
> **No double, of any kind.** No mocked filesystem, no mocked coverage report, no synthesised project tree, no fixture `testing.md`, no stand-in for `aidd-dev:06-test`. The first real read of a real repository is the test — a suite that passes against a double proves the double.
>
> Reference fixtures:
> - **`app`** — `C:\Users\fxgui\Documents\Perso\Projects\suddenly\_code\app`. 80 test files; gate `make check`; `tests/test_federation.py` and `tests/test_federation_e2e.py` supply the **external boundary** exclusion case. Enough files that a user-named batch is a realistic request.
> - **`ai-hub`** — `C:\Users\fxgui\Documents\Perso\Projects\suddenly\_code\ai-hub`. 50 test files; `tests/e2e/`; **no phase declared**, so a switch is exercised by declaring one (see `phase-scenarios.md` S6 for the `undetermined` question itself). No coverage artefact of any kind.
>
> **On the excluded categories.** The page names **three** categories plus a catch-all: external-boundary tests, tests a consequence criterion retains anyway, sole-safety-net tests — and *any test that **either** of the two motives fails to qualify*. The catch-all follows from the conjunction: the batch requires both motives, so failing one is enough to be out. A run that treats the catch-all as a fourth named category is not wrong; a run that reads it as "neither motive qualifies it" has inverted the quantifier and will build a batch on a disjunction.
>
> **On the matrix, in this suite.** The `phase × niveau` matrix produces exactly two things — a required proof form and a number — and neither is an approval unit. S15 and S16 exist so that no part of the matrix leaks into the removal side of this regime: a cell marked `—` requires nothing and therefore qualifies nothing for removal, and a saturated ceiling is a refusal to add, never a demand to give something back.
>
> **Declared ambiguity, not resolved here.** The page settles the named-batch regime for removals (`### Un lot que l'utilisateur nomme lui-même`) and, by exclusion, for additions (same section — *jamais pour les ajouts*) — but says nothing about the third act, a **configuration fix**, which is neither a removal nor an addition. This suite does not invent a rule for it: no scenario here tests whether a configuration-fix batch may be user-named. That gap belongs to the page, not to this suite, to close.

## How to run

Agent-as-`overcode:control` (dry-run, READ-ONLY on the fixture): for each scenario, load **only** the files in its *Judge load path*, plus this suite. Reason out the response and — the load-bearing observable here — **the exact unit of approval the skill would request**, then judge against the pass criteria.

**S1, S2 and S3 are the three confirmable acts, tested separately, not as one bundled scenario.** Each act — removal, configuration fix, proposed-test write — gets its own row and its own verdict; a run that confirms two of the three is not "mostly passing", it is two PASS and one FAIL.

**S5 and S6 are the asymmetry and must be judged as a pair.** They differ only in the direction of the act; a skill that treats them the same has lost the model regardless of which way it errs. Score S5 → S6 → the pair, and record the pair verdict separately. **The asymmetry is no longer absolute, and that is the point of the pair**: a removal batch is accepted unconditionally because a removal only loosens the constraint, while an addition batch is accepted *within the margin* — a run that has flattened the two into one permissive rule fails the pair even if both rows land the right act.

**Note — S6 rewritten (2026-07-29), its run-2 PASS is void.** Run 2 scored S6 PASS against `04-strengthen.md:73` (*No named batch on the addition side*), an instruction that no longer states the rule in force: `docs/control.md` § *Un lot que l'utilisateur nomme lui-même* now admits an addition batch within the remaining margin of every cell it touches, the blanket prohibition having been written under a **moving** constraint (the project density) and losing its ground once the binding constraint is a **fixed** per-cell ceiling. The row is **rewritten, not deleted** (DEC-006), and it is expected **red** until the skill catches up — it left the green-witness set deliberately, and its turning red is not a regression signal.

**Friction: a correct act reached for the wrong motive is a friction; the verdict cell reads `FAIL` with the note "act correct, motive wrong"; friction is never a PASS.** S6, S10, S14 and S16 each judge a stated motive, not only an outcome, and are scored as **assumed yellows** under this rule — a run that lands the right decision on the wrong reasoning fails that row, it does not pass with a caveat.

**S15 and S16 are the matrix's two exits into this suite, and both now require a positive statement, not silence.** S15 requires the run to **name the cell** (`hardening × ordinaire`) and **state**, in words, that a cell without a requirement qualifies no removal — an empty batch produced without that statement is a FAIL, not an acceptable quiet pass. S16 requires the saturation figure to be sourced only from the stated premise (never from a file count) and requires the removal exit to be named without being proposed. Passing on silence is a defect in both, not a friction and not a PASS.

**The `Page rule pinned` column is for the maintainer, not for the judge.** It records which rule of `docs/control.md` a row protects, so that a page edit can find the scenarios that guard it. The judge never loads the page — its reading is bounded by the *Judge load path* column.

**Decisive observables** (write-scoped):

- **The approval unit, per act.** Line, user-named batch, or switch batch — recorded explicitly for every scenario.
- **Four components or the batch is invalid.** Count them; do not accept "a summary and a list".
- **The intended write, not a promise.** For the exhaustive-list component of S8, the observable is the **path and the full content** the run states it would write, before the question is asked — a path with no content, or content deferred to after the question, is a FAIL.
- **No per-item fallback after a refusal.** Any continuation is an automatic FAIL.
- **No net-balance target.** The figure is a constat; any goal framing is a FAIL.
- **Removal proposals originating from the matrix = ∅.** Counted over S15 and S16 together; one is enough to fail the pair.

**Rewrite log — S13's named path, 2026-07-29 (DEC-006).** The row was rewritten, not deleted, and the motive is that it named a file that does not exist. `tests/test_notifications.py` is not on `app`; run 6 judged it by substituting a real out-of-domain test, `tests/core/test_version.py`, under *Adapt surface, keep behaviour*. A suite that requires every run to perform the same substitution has moved a fixture fact into the judge's discretion — and the *no double* rule of this suite exists precisely to keep fixture facts on disk. The row now names the path run 6 used, verified present. **The behaviour under test is untouched**: both stated premises are still weighting inputs, and neither still qualifies a removal.
